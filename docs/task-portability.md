# CAD AI Bridge 跨项目、跨任务实施与验收

2026-10-21按用户要求校正：医院是示例。产品目标是理解复杂工程任务，形成有依据、可编辑、自检完整、可供专业人员审核的成果。本文补充[总方案](engineering-design-plan.md)，替代其历史记录中把后续主线限定为医院缺项的优先级；历史证据及未通过状态不变。

## 现有能力与真实边界

| 层次 | 已有依据 | 尚未达到 |
| --- | --- | --- |
| 通用CAD操作 | 查询/完整捕获、对象编辑、图面输出、保存重开、来源绑定统计和规则检查等既有能力 | 执行指令成功不等于理解工程任务；本次未重新进行全部原生CAD验收 |
| 工程设计流水线 | 照明专业契约保留；空间方案独立契约/求解/自检/原生图纸已接入同一任务入口 | 专业模型仍分别维护；共用资料/房间清单/用途变更与跨专业协调尚未完成 |
| 专业计算 | 有边界的普通照明计算、光度及有界优化 | 新增有界办公空间方案；医疗全电气、任意建筑布局及其他专业没有因此获得能力认证 |

| 新增通用任务入口 | 无专业字段的任务身份契约、已注册能力路由、适配参数校验、持久化收据及当前状态；已知A/B/C任务经真实MCP/CAD切换和新进程重放核对 | 空间方案已为独立第二设计包；通用语义理解、跨包协调和未见项目迁移仍未验收 |
| 新增通用依赖记录 | 声明的来源/要求/标准/条件/成果依赖，标量一致性，前后快照及CSV影响；已用实际需求修订、两版原生出图与分析验证 | 不自动理解标准、推断漏边或识别伪装的对照；仍为全模型保守重算，不是选择性CAD更新 |

## 开发顺序

1. P0：冻结能力清单、任务类别及接口边界。通用任务保存项目身份、输入角色/摘要、任务依赖、需求来源/冲突、版本、执行预算、产物、验收和审核；不得强制具有房间、灯具、回路或医院分类。专业包提供输入校验、适用性、求解、编辑、独立校验、图纸及影响分析接口。现有照明入口保持兼容，逐步由其适配器承接。
2. P0：能力匹配与隔离。根据实际安装的能力及所需输入，明确可执行、待补资料和未支持范围。未支持设计不得静默降级为文字替换或普通照明；可用的CAD查询/编辑仅作为明确标注的局部操作。来源、标准、产品、模型、缓存、输出和审核按项目/任务/版本隔离；跨包共用资料必须显式引用并检查版本。
3. P0：每个底座变更同时运行原照明回归和至少一项非照明流程。当前选择来源绑定的几何统计及图纸文字规则检查作低成本执行层回归，不能用它们抵扣第二类复杂设计验收。整层光度预算继续作为照明包的限时工作项；真实运行前不改变计算精度和质量阈值，也不宣布性能验收。
4. M2：完成首个专项质量门槛，补齐医院/办公/教学三类项目的资料与适用性差异。医院资料不足就保持该用例缺项，其他有独立输入的开发继续；不反复为同一医院特例写入底座分支。
5. M3：新增办公空间平面方案能力包，以房间需求、邻接、面积与现状约束形成方案、房间表和可编辑图，再进行修改、自检、出图和审核。明确其建筑/消防/无障碍等需验证范围；不能把碰撞检查或面积统计包装成设计。待该包能够独立工作后，验证空间变更对照明的影响及跨包重算。
6. M4：冻结实现后，按下表进行独立项目、真实客户端、专业审核及新机器验收。发现问题需保留失败轮，修复后重测受影响项及原能力，不能修改参考答案让结果通过。

目标接口仍在逐步实现。现已增加无专业字段的任务身份契约、显式能力适配与持久化执行收据，真实入口见[通用任务入口](engineering-tasks.md)。两类设计保有独立专业模型；共用资料/空间清单/用途变更契约与跨包协调尚未完成；不能将外层契约和路由完成称为通用复杂设计完成。

## 验收矩阵

| 轴 | 最低门槛 | 当前证据与状态 |
| --- | --- | --- |
| 项目类型 | 医院、办公、教学至少三类；分别声明支持空间及专业范围 | 医院回溯和已知合成办公/教学相关样例，不是三类独立迁移通过 |
| 复杂任务类型 | 普通照明设计 + 办公空间平面方案，两类均包含新建/编辑、自检、可编辑出图和待审 | 照明已有有界通路；空间包已完成开发用例的方案/改版、自检及两版原生图，专业/独立客户验收待完成；查询/文字检查不算第二类 |
| 未见独立输入 | 至少3个真实项目，独立人员在开发后提供任务和对照；覆盖上述类型和任务，不能全部使用照明；项目不足时不得记通过 | 尚未取得；不得将开发者继续编写的变体称为未见输入 |
| 任务切换 | A照明→B非照明→A；以及项目A→同专业项目C→A；来源/单位/标准/历史状态正确，显式更新输入才可改变原任务 | 已知合成A/B/C任务的持久化身份、独立捕获分析、回到A原生出图及新进程重放通过；新增两类设计包已知切换通过；跨包协调、标准/依赖共用和未见真实项目迁移仍未验收 |
| 需求与专业质量 | 关键需求100%来源可追且覆盖，一般需求≥95%；重要约束缺失阻断受影响范围；跨图/表一致，无缺图断链；专业重大问题0 | 仅已声明子集，通用及跨包门槛未通过 |
| 速度和人工负担 | 每个任务在看结果前冻结用时、资源、人工修正预算；记录失败、重试、人工操作及最终返工；通过质量门槛后再比较效率 | 无独立项目可支持效率或竞争领先结论 |
| 回归与交付 | 已验收任务的阈值不放宽；相同输入保持允许误差内的质量和完整性；真实CAD重开/PDF查看/交付下载逐项核对 | 本次353项单元和3项静态检查；空间包两版原生图及已知跨包状态切换通过，未见项目迁移待审 |
| 真实使用 | 干净机器、外部用户、实际客户端到出图，以及真实专业审核分别记录 | 尚未通过，不得用测试数量抵扣 |

案例名称、医院房间特例、最终灯位和对照数量不得进入通用决策分支；对照只用于冻结结果之后的比较。新增类型时提供专业能力与证据，不添加“识别到医院/学校名称就套模板”的逻辑。

## 当前增量的发布边界

本轮同时在开发照明整层分区、预算、取消和并发控制。单元验证与实际Radiance/CAD运行分开记录；默认串行。显式双并发已完成一个12房间失败候选的全范围计算，但未通过整层质量/性能验收；独立单办公室验证了新质量注释原生出图，不能抵扣楼层失败。详见[本轮实测](whole-floor-quality-validation.json)。原计算阈值和物理设置不因速度问题放宽。冻结v2.0发行包不重打包，历史审核文件不覆盖。

脱敏结果见[本次验证记录](task-portability-validation.json)。M2—M4仍未完成，医院示例跑通也不会自动将它们标记完成。


## 第二设计包增量

office-space-planning已独立完成开发用例的新建、程序改版、自检、两版可编辑DWG和成套待审图。真实MCP验证照明A→空间B改版/交付→空间C→照明A；同名房间ID不跨项目复用来源/模型，旧收据与当前版本分别返回，新只读进程验证文件。首轮图面问题保留，修正后十页逐页检查通过。详细边界见[接口](engineering-tasks.md)和[验证](space-planning-validation.json)。

这里覆盖两类复杂设计包的已知状态隔离，未覆盖空间设计结果联动照明的跨专业重算。源边界仍是程序声明、真实资料接入和语义解释未验证；二十房间上限、两侧直走廊矩形房间族、项目尺寸子集、标准/消防/无障碍/采光/声学/施工待审必须向用户显露。下一步先共用资料/房间清单/用途变更及实际源绑定，再做空间→照明影响，不能将合成变体当未见项目或把M3/M4记为完成。
